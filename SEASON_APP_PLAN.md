# Season App Plan

Scope: extend the draft tool into a season-long companion — schedule, draft
order/results, standings, roster, and weekly lineup/waiver recommendations —
built on top of your actual ESPN league. Scope decided 2026-08-31:
**read-only + recommendations, not automated transactions** (see "Why not
read-write" below).

## Why this needs ESPN, not just our existing sources

Sleeper/FantasyPros/nflverse know about NFL players. They know nothing about
*your league* — who's on your team, who you play each week, what order the
draft went in. Those are ESPN concepts, generated by ESPN, for this specific
private league. There's no way around at least a read-only ESPN integration
if "my schedule" and "draft order" are going to mean anything real.

ESPN has no official public API, but a years-old, well-documented unofficial
one exists (the same one every open-source ESPN fantasy tool uses):

```
GET https://fantasy.espn.com/apis/v3/games/ffl/seasons/{season}/segments/0/leagues/{leagueId}
    ?view=mTeam          (teams, standings)
    &view=mRoster         (who's on every roster)
    &view=mMatchupScore   (weekly schedule + scores)
    &view=mDraftDetail    (draft order + results, once ESPN generates them)
```

For a private league (yours), this requires your ESPN session cookies —
`espn_s2` and `SWID` — sent as request headers. These prove you're logged in;
anyone with them can act as you on ESPN. That's the whole reason this plan
draws a hard line at read-only.

## Why not read-write (making actual transactions/lineup changes)

Decided against, for now:

- ESPN's *write* endpoints (set lineup, add/drop, propose trade) are far
  less documented in the community than the read ones — more likely to
  break silently, harder to get right the first time.
- Doing it from a public static site means either shipping your session
  cookie to the browser (anyone visiting could act as you) or standing up
  a real backend to hold it server-side — a genuine architecture change,
  not an extension of what exists.
- A bug in an automated transaction has real consequences: an accidental
  drop or a bad auto-set lineup affects your actual team, not just a
  report.

Read-only gets most of the value (know your schedule, know what to do)
without any of that risk. You still click the actual button on ESPN.

## Phase 1 — ESPN read-only sync

New pipeline step, same shape as every other fetch script:

- `pipeline/src/sources/espn.ts` — authenticated fetch helper (cookies from
  env vars, never committed).
- `pipeline/src/fetch-espn-league.ts` — pulls teams/standings, rosters,
  schedule/matchups, and draft results (empty until ESPN generates them,
  ~1hr before your Sep 6 draft per league settings) into
  `data/processed/espn-{teams,rosters,schedule,draft}.json`.
- New GitHub Actions secrets: `ESPN_S2`, `ESPN_SWID` (sensitive — repo
  secrets, injected as env vars, never logged or written to a JSON file).
  `LEAGUE_ID` and `MY_TEAM_ID` aren't sensitive but travel alongside them
  for simplicity.
- Wire into the existing `update-data.yml` scheduled workflow.

**Unknown worth flagging honestly:** ESPN's API is unofficial. It's been
stable for years (this is how the whole open-source ESPN-fantasy tooling
ecosystem works), but "unofficial" means it could change without notice.
Low risk, not zero.

## Phase 2 — Frontend: "My League"

New tabs alongside the existing Table / Draft Night toggle:

- **Schedule** — your weekly matchup list, opponent highlighted.
- **Draft** — pre-draft: the draft order once ESPN sets it. Post-draft: the
  full draft board (every team's picks, in order) — laid out next to our
  own VBD rank for each pick, so you can see at a glance how the room's
  picks compared to our model (e.g. "taken 8th, our board had him #1
  overall" — reuses the same rank-delta idea already in the table view).
- **Standings** — records, points for/against, once the season's underway.
- **My Roster** — your actual current roster from ESPN, cross-referenced
  with our own projections/VBD per player (so a bench player quietly
  outperforming a starter is visible immediately).

## Phase 3 — Weekly lineup recommendations

The real ongoing value, and the part that needs genuinely new modeling:
everything the pipeline computes today is a **season total**. A weekly
lineup call needs a **per-week** projection instead — this is new work, not
a repackaging of what exists:

- Per-week projected points per player (recency-weighted across recent
  *weeks*, not seasons).
- Ideally opponent-adjusted per week (extending the existing
  strength-of-schedule idea from season-level to week-level).
- A small optimizer: given your actual roster and league's starting
  requirements (1 QB/2 RB/2 WR/1 TE/1 FLEX/1 K/1 D/ST), pick the
  combination that maximizes total projected points for that week —
  simple assignment problem, not complex given a ~16-player roster.
- Output: "start these 9, bench these 7," with the projected-points
  reasoning shown (reusing the player-card explanation pattern already
  built).

## Phase 4 (stretch) — Waiver-wire recommendations

Compare your roster against currently-unrostered players leaguewide (from
ESPN's real roster data, not just our local Draft Night state) using the
existing VBD rankings: "these available players out-project someone on
your bench."

## Sequencing

Phase 1 unlocks Phase 2 (nothing to show without the data). Phase 3 is
independent extra modeling work and can start once Phase 1's roster/
schedule data exists. Phase 4 is genuinely optional — build it only if
Phase 3 turns out to be as useful as expected and there's appetite for more.

## What's needed from you before Phase 1 starts

Your ESPN session cookies, so the scheduled pipeline can read your private
league:

1. Log into fantasy.espn.com in your browser, open your league.
2. Open dev tools (F12 or right-click → Inspect) → Application/Storage tab
   → Cookies → `https://fantasy.espn.com`.
3. Find `espn_s2` (long string) and `SWID` (looks like `{...-...-...}`).
4. These go straight into GitHub repo secrets — never into a file, never
   committed, never visible in the public site's code.

Also need your league ID (visible in the ESPN league URL) and which team ID
is yours.
